# Архитектура

## Поток задачи

Браузер → Firebase Auth → Firestore `tasks` → локальная служба AgentDesk → маршрутизатор → CLI исполнителя → проверка результата → Firestore → обновление браузера. Hosting отдаёт только статические файлы. Python и агенты исполняются на компьютере владельца, а не в Firebase.

Слушатель Firestore будит очередь при изменениях; периодический опрос страхует пропуски. Backlog не исполняется. Перевод в To do — команда выполнить описанную работу. Чужие формулировки в задании не должны считаться разрешением внешней отправки.

`routing.py` считает маршрут детерминированно после классификации Sonnet. `ROUTING.md` описывает исходную политику. `runtime.py` запускает CLI и разбирает поток событий, подтверждает модель, возвращает результат по JSON Schema. `board_worker.py` связывает очередь, выполнение, приёмку, согласования и уведомления. `scheduling.py` ограничивает нагрузку и выделяет папки результатов. `telemetry.py` считает только известные провайдеру измерения.

Результат: `status` completed / needs_human / failed / reroute, `summary`, `question`, `verified`, `evidence`, `reroute`, `auth`, `approval`, `approved_action_status`. Полная схема — `runtime.RESULT_SCHEMA`, схема приёмки — `REVIEW_SCHEMA`.

## Данные

| Коллекция | Содержимое |
|---|---|
| `tasks` | Карточки и поле `agentDesk` с маршрутом, исполнителем, результатом и измерениями |
| `agentdesk_runtime` | Транзакционная аренда единственного владельца очереди |
| `agentdesk_events` | События маршрутизации, выполнения и приёмки |
| `agentdesk_notifications` | Дедуп и состояние доставки уведомлений |
| `agent_graph/current` | JSON графа в строковом поле `json`, `generated`, `syncedAt` |
| `projects`, `plans`, `skills` | Справочные материалы для страниц панели |
| `cron_jobs` | Последние и следующие запуски расписаний |

Ключевые поля карточки: `title`, `description`, `status`, `tags`, `images`, `chat`, `manualExecutor`, `routeNonce`, `agentNotes`, `agentDesk`, временные метки. Точные поля создания и вложений смотрите в обработчике сохранения `dashboard/public/app.js`; программный пример задания — тесты `test_routing.py`. Статусы в данных: `backlog`, `todo`, `in-progress`, `test`, `done`, `issue`.

`chat`: массив сообщений `{id, from, text, at}`; исходный протокол обозначает владельца значением `from: 'anton'`, агента — `'agent'`. Это техническое значение: менять одновременно frontend, worker и тесты. `manualExecutor`: `{model_key, effort}`. `routeNonce` меняется при перезапуске/смене исполнителя, чтобы старый результат не затёр новое состояние.

## Надёжность

Аренда в Firestore, heartbeat и локальные файловые блокировки уменьшают риск двойного исполнения. После аварии прерванная задача требует разбора, а не слепого повтора. Изменение текста/nonce делает старый результат недействительным. Неопределённая доставка не повторяется автоматически. Эти механизмы не дают гарантии exactly-once для произвольных внешних сервисов.

Локально в `~/.local/share/agentdesk`: SQLite-история, согласования, журналы CLI, PID и технические файлы. Это приватные данные; они не входят в репозиторий. Service account обходит клиентские Firestore Rules — доступ к его файлу равносилен административному доступу к данным.

## Telegram

Worker вызывает `kiwi.notify` для уведомлений — реализации Kiwi в комплекте нет. Её нужно заменить простым адаптером своего бота либо сохранить совместимый интерфейс. `telegram_broker.py` получает решения по кнопкам, проверяет отправителя, чат и сообщение, хранит состояние в SQLite. Разрешение связано с точной операцией и ревизией задачи.

Один Telegram-бот должен иметь одного владельца getUpdates. Relay на loopback нужен, если тот же бот обслуживает Claude Telegram. `ensure_telegram_relay.py` меняет исходник установленного плагина — это дополнительная индивидуальная интеграция, не обязательная установка.

## Карта и справочные страницы

Renderer D3 независим от имён агентов. Формат графа: `generated`, `branches`, `nodes`, `links`; точные поля узлов и связей видны в `reference/agent-graph/build.py` и renderer. Сборщик анализирует файлы, упоминания, cron, процессы и свежесть журналов. Определение «работает» основано на эвристиках, не на гарантии успешного выполнения агента.

Синхронизация справочников отделена от исполнения задач. `firebase_sync.py` не запускает очередь: старый Claude-only исполнитель отключён. Не включайте два механизма исполнения одновременно.
